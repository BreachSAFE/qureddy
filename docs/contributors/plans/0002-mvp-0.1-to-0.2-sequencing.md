## Why a plan, not just issues

This project has 30+ open issues spanning bugs, refactors, design decisions, and infrastructure. Each issue is correctly scoped on its own merits. **The dependencies between them are not.** Without a written sequence:

- New contributors pick whichever issue looks small and bounce off blockers (e.g. "I'll fix #28 deterministic JSON" → discovers #28 is blocked on #76 → blocked on #60 cli refactor → drops the work).
- Two sessions pick the same issue independently. (Already happened this week with #60 + #82 — see #82's filing context.)
- Decision items (#13, #18, #21) wait silently for a maintainer call that nobody knows is owed.
- Refactor work that unblocks downstream bug fixes gets deferred because the bugs feel more urgent — but the bug fixes won't land cleanly until the refactor does.

This plan is the operational view. It names every open work item, identifies what blocks what, and orders the waves.

This plan **does not replace ADR 0005**. The ADR is the design lock for the cli.py and openssl_probe.py splits — what the result looks like. This plan is when each thing happens and what depends on what.

## How to use this plan

- **Reading order:** the waves below are ordered. Wave A is the critical path; everything depends on it.
- **Within a wave:** work items are ordered by leverage (most-unblocking-first), but parallel-safe items are explicitly marked.
- **Maintainer-decision items** (Wave B-decisions) require Paul's input before any implementation can start. Flagged with **🔒 NEEDS MAINTAINER**.
- **Each work item** has: issue # / title / blocks / blocked by / scope / acceptance gate. Cite this plan in PR descriptions for traceability.

## Wave A — Infrastructure (BLOCKING — fix before anything else)

Without these, every later piece of work is harder or unmeasurable. Land in this exact order.

### A.1 — Fix CI infrastructure failures

**Issue:** [#70](https://github.com/breachsafe/qureddy/issues/70) — `ci: GitHub Actions runs fail before step logs are emitted, leaving Phase 1/Audit failures unactionable`

**Why first:** Every PR currently shows red CI even when the PR's diff is clean. Verified on PR #47 and PR #97: failed jobs have empty `steps: []`, meaning the runner died at bootstrap before any step ran. Reviewers can't tell "PR is broken" from "CI infrastructure is broken." This poisons every other gate decision.

**Blocks:** every PR's "is it ready to merge" question. The `validate-fix` skill cannot run if Phase 1 dies before the test step.

**Blocked by:** nothing.

**Scope:** GitHub Actions YAML / workflow infrastructure. No source-code change.

**Acceptance gate:**
- [ ] At least 3 PRs in a row reach Phase 2 (Unit) without Phase 1 dying with `steps: []`.
- [ ] On a known-clean PR, all 7 phases run to either PASS or actionable FAIL — no infra silence.
- [ ] `gh run view --log-failed <run-id>` returns a real log when a phase fails, not "BlobNotFound".

**Estimate:** 1-3 hours of CI debugging. No Python knowledge required; YAML/Actions expertise.

### A.2 — `audit-docs` skill follow-ups: deterministic check script + CI wiring

**Issue:** [#91](https://github.com/breachsafe/qureddy/issues/91) — `[feat] skill: audit-docs — detect drift between docs and code`

**Why second:** The skill itself is landed (PR #93). The deterministic check script (`scripts/audit_docs.py` for Class B/C/D) and CI wiring are open. Without CI wiring, doc drift only gets caught when someone manually invokes the skill. With CI wiring, drift fails the gate the same way file size does.

**Blocks:** sustained doc/code consistency (cosmetic — not blocking other work).

**Blocked by:** A.1 (CI must work for the new gate to mean anything).

**Scope:** New `scripts/audit_docs.py` (Class B/C/D, Class A stays interactive). Wire into `just gates` and add a non-blocking CI step (warn-only, like Semgrep).

**Acceptance gate:**
- [ ] `scripts/audit_docs.py` exists; runnable via `just audit-docs`.
- [ ] Script catches at least one known-real drift case (e.g. CLAUDE.md test-file count) and reports it.
- [ ] CI runs the script as a non-blocking warning step.

**Estimate:** 4-8 hours. Contained.

## Wave B — Decisions (NEEDS MAINTAINER — unblock these before Wave C)

Three open issues require product/UX decisions from Paul before implementation can start. None are large; all are blockers for downstream bug fixes.

### B.1 🔒 — `--sni` for IP targets: enforce or relax?

**Issue:** [#18](https://github.com/breachsafe/qureddy/issues/18) — `cli: --sni is documented as 'required for IP targets' but parse_target accepts IP without it silently`

**Decision:** Option A (reject IP without `--sni`, exit 4) or Option B (accept with WARN log)?

**Trade-off:**
- **Option A:** matches the help text. Stricter. Breaks workflows that scan private-IP TLS endpoints with no virtual-hosting (uncommon).
- **Option B:** friendlier. Accepts user intent. Surfaces the issue at runtime via warn-then-fail. Less truthful documentation.

**Recommendation:** Option A. Matches help text; Option B is friendly but produces misleading SNI failures.

**Blocks:** the implementation of #18.

**Estimate to decide:** 5 minutes of Paul's time.

### B.2 🔒 — Timeout `return_code`: nullable or sentinel?

**Issue:** [#21](https://github.com/breachsafe/qureddy/issues/21) — `scanner: timeout return_code=-1 collides with SIGHUP convention; consumers cannot distinguish`

**Decision:** Make `ProbeResult.return_code: int | None` (schema change) or use an out-of-range sentinel like `255 + 1000` (no schema change)?

**Trade-off:**
- **Nullable:** clean Pydantic model. Schema bump (`qureddy.scan.v1` → `v2`). Affects every downstream JSON consumer.
- **Sentinel:** no schema change. Magic number harder to discover than `null`. Conflicts with the project's "frozen schema = stable contract" principle.

Plus: introduce `FailureCategory.PROBE_TIMEOUT` (enum extension on a frozen field). Same maintainer-call territory.

**Recommendation:** `int | None` + new `FailureCategory.PROBE_TIMEOUT`. Schema bump is honest about the partial-execution shape. Update `mvp-implement` skill model field locks at the same time.

**Blocks:** the implementation of #21 AND #11 (which proposes `UNKNOWN_FAILURE` enum extension on the same frozen surface — same decision).

**Estimate to decide:** 15 minutes including reading the trade-off in #21's body.

### B.3 🔒 — Internal exit code: 70?

**Issue:** [#12](https://github.com/breachsafe/qureddy/issues/12) — `cli: top-level Exception handler exits 2 (target failed) for internal qureddy bugs`

**Decision (already made? verify):** Add `EXIT_INTERNAL_ERROR = 70` (BSD `sysexits.h` `EX_SOFTWARE`) to the exit-code surface?

**Status check:** Reviewing the code: `cli.py:62-66` shows `EXIT_INTERNAL_ERROR = 70` is already defined and `docs/reference/exit-codes.md` documents it. **This decision appears already made.** If so, B.3 is closed and not blocking.

**Action:** verify and either close or fold into the implementation tracker.

## Decision rules for picking the next thing

When a contributor has a free slot, decide what to pick by walking this tree:

1. **Is anything in Wave A still open?** → Fix that first. Everything else is harder without it.
2. **Are any Wave B decisions still pending?** → Surface them to Paul. Don't implement Wave C.x or D.x that depends on them.
3. **Is C.1 (#60) still open?** → Pick that. Critical path.
4. **Are any of C.2-C.6 still open and unblocked?** → Pick the smallest one matching your expertise.
5. **Are any Wave D bugs unblocked?** → Pick the smallest with a clean dependency.
6. **Otherwise:** pick a Wave E or F item that matches your interests.

If two contributors pick the same item, the second to pick comments "I'll take #82 instead" and re-walks the tree. **Do not duplicate work.**
